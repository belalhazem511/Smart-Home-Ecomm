# دراسة تصميم واجهة Smart Home Marketplace

الإصدار 1.1 — 23 نوفمبر 2026. النطاق: دراسة وتصميم قواعد التنفيذ، ولم يبدأ بناء الموقع. التقنية المؤكدة من المستخدم: **React + JavaScript + Tailwind، وأنيميشن CSS بسيطة**. اللغة مؤكدة: **English أولًا بالكامل، باتجاه LTR؛ ثم العربية وRTL بعد اكتمال النسخة الإنجليزية ومراجعتها إلى آخر خطوة**. الاسم والهوية والألوان النهائية لم تُعتمد بعد. لغة هذا التقرير عربية لشرح الدراسة، وليست لغة واجهة الإصدار الأول.

## 01 — نتيجة الدراسة والاتجاه المقترح

أنسب اتجاه للمشروع: متجر تقني واضح، بخلفيات فاتحة وصور منتجات كبيرة، ومساحات محسوبة، ومعلومات شراء ظاهرة. الرئيسية تعرض استخدامات البيت الذكي؛ صفحات التصنيفات تساعد على المقارنة؛ وصفحة المنتج توضح المنتج والبائع ومتطلبات التشغيل قبل الدفع. هذا استنتاج تصميمي للمشروع، وليس نتيجة اختبار مستخدمين أجريناه.

نأخذ من Gizmos تنظيم المتجر، ومن INPOWER الفلاتر وملخص السلة، ومن BR.F وضوح صفحة المنتج، ومن Echoform وVoltix جودة عرض الصور وتسلسل العناوين. لا نجمع كل ألوانهم وتأثيراتهم في صفحة واحدة. تأثيرات العرض المائل والإطار الكبير في بعض الصور جزء من تقديم التصميم، وليست بالضرورة عناصر داخل الموقع.

مقياس نجاح الواجهة: هل يقدر العميل يلاقي جهاز مناسب، يعرف ما يحتاجه لتشغيله، يقارن البائعين، ويفهم إجمالي طلبه؟ الشكل يخدم الخطوات دي. التوصية البصرية الأولية: أبيض ورمادي بارد، نص داكن، أزرق أساسي، وصور منازل حقيقية. الأزرق مقترح قابل للتبديل من ملف ألوان واحد.

## 02 — المنهج وحدود الدقة

اعتمدت الدراسة على **11 صورة مرجعية من المستخدم**، ومصادر رسمية من eBay وnoon وApple وIKEA وAqara، وتوثيق React وTailwind وW3C وMDN وweb.dev، وأبحاث أصلية من Baymard. المصادر وروابطها في آخر الدراسة.

| نوع المعلومة | ماذا تعني؟ | الثقة |
| --- | --- | --- |
| ملاحظة من الصورة | توزيع، كثافة، شكل زر، تباين بصري | جيدة في الصور الكبيرة؛ محدودة في المصغرات |
| قياس بكسل الصورة | إحداثيات داخل JPEG المرسل | يمكن قياسه تقريبًا؛ ليس CSS px |
| معلومة من مصدر رسمي | سلوك أو قاعدة موثقة | حسب الصفحة المسترجعة وتاريخها |
| رقم تنفيذ مقترح | قيمة نختارها لنظامنا | قرار تصميم يحتاج تجربة فعلية بالمحتوى |

لا توجد ملفات Figma أو قياسات DOM للمراجع المرسلة. الصور المصغرة والمنظورية لا تكشف الخط الأصلي أو الـbreakpoints أو جميع حالات التفاعل. لذلك **كل مقاسات التنفيذ أدناه مقترحة لنظامنا**، ولا ننسبها لأمازون أو نون. لا يمكن استنتاج جودة backend أو أمان الموقع من شكله.

صفحة Amazon.eg الرئيسية لم تُسترجع بنجاح أثناء الدراسة، ورئيسية noon تعذر فتحها مباشرة؛ أمكن مراجعة صفحة منتج noon وصفحات رسمية أخرى. تحليل أمازون هنا محدود للمعلومات المنشورة عن البائع والتنفيذ، وليس فحصًا بصريًا حيًا أو قياسًا لواجهته. الصفحات التجارية قد تختلف حسب اللغة والمكان والحساب وتجارب A/B؛ لا نعتمد أسعارها أو مواعيدها كبيانات للمشروع.

### مثال قياس يمكن الدفاع عنه

في R02، حدود منطقة المحتوى تقريبًا من x=100 إلى x=1117 داخل صورة عرضها 1200 بكسل؛ عرض يقارب 1017 بكسل صورة. الـhero تقريبًا 1017×318، أي نسبة نحو 3.2:1. هذه إحداثيات تقريبية داخل الصورة، وليست دليلًا أن container الموقع 1017 CSS px. نستخدم النسبة لفهم تركيب المرجع، ثم نختار container مستقلًا مناسبًا للتنفيذ.

لم نعتمد قيم HEX مأخوذة من كل الصورة كهوية؛ الصورة تضم خلفيات العرض وصور منتجات وضغط JPEG. الألوان الدقيقة المقترحة في قسم 06 قرارات لنظامنا، وليست ألوان البراند الأصلية لتلك المراجع.

12px لمعلومة قصيرة غير أساسية؛ لا نخفي عليه ضمانًا أو تكلفة. سعر واضح وعملة واضحة؛ تنسيق Intl حسب اللغة، مع اختبار الاتجاه. لا نزيد letter-spacing على العربي. عنوان الكارت سطران ثابتان في العرض المعتاد مع رابط للتفاصيل، ونتيح التمدد عند التكبير بدل قص المعلومات الأساسية.

اشتراك البروتوكول وحده لا يثبت توافق الجهازين. المعلومات تأتي من catalog موثق، وتُراجع عند تعديلها. لا نعرض شهادات أو شعارات توافق لا يملك الكتالوج دليلها. منصة التجارة لا تطلب كلمة سر Wi‑Fi للبيت أو حساب الشركة المصنعة أثناء الشراء. خدمة التركيب امتداد مؤجل بحسب التحليل الأساسي، فلا نعرض زر «احجز فني» عاملًا قبل تنفيذها.

صفحة المنتج تفصل Product وVariant وSeller Offer: تغيير البائع قد يغير السعر والشحن والضمان؛ تغيير الـvariant قد يغير الصورة والمتطلبات. تحذير واضح عند تغيير عنصر مؤثر، ثم تحديث quote. «ابتداءً من» يتطلب أدنى عرض صالح فعلًا، ولا يعني إجمالي السعر مع الشحن.

## 10 — الواجهة الديناميكية وحالاتها

الديناميكية تعني بيانات حقيقية وحالات متماسكة، مع مرونة عرض المحتوى. لا تعني بناء page builder أو component يقبل عشرات الأوضاع.

| المجال | مصدر الحقيقة | سلوك الواجهة |
| --- | --- | --- |
| بحث وفلاتر وترتيب وصفحة | URL + نتائج API | مشاركة الرابط، رجوع صحيح، مسح مفرد/كامل؛ داخل المجموعة OR وبين مجموعات مختلفة AND وفق عقد API |
| قائمة الفلاتر في drawer | draft محلي قبل Apply | الإلغاء لا يغير النتائج، التطبيق يحدث URL مرة ويعيد الصفحة للأولى |
| السعر والتوفر | offer وquote من الخادم | إظهار pending؛ عند تغير السعر يراجع العميل الفرق قبل التأكيد |
| السلة | عناصر العرض/variant والكمية؛ تسعير الخادم | مفاتيح ثابتة تشمل offer/variant؛ لا ندمج بائعين بالخطأ؛ لا ندعي حجز المخزون بمجرد الإضافة |
| الطلب والدفع | order/payment status API | صفحة العودة من الدفع ليست إثبات نجاح؛ pending/unknown لهما تصميم واضح وإعادة تحقق منضبطة |
| العناوين والتوصيل | API بعد إدخال العنوان | estimate قبل العنوان، وعدم اختراع تاريخ وصول |
| الصلاحيات | الخادم | إخفاء زر تحسين UX فقط؛ 401 و403 لهما تعامل مستقل |
| محتوى حملات الرئيسية | بيانات محدودة البنية | hero وcategories وproduct sections؛ لا محرك بناء صفحات عام |

لكل شاشة بيانات: loading، empty، error، success؛ وللشراء: unavailable، pending، unknown، rejected، changed price، session expired عند الحاجة. skeleton له أبعاد الكارت؛ لو ظهرت بيانات قديمة أثناء تحديث الفلاتر نعلّم أنها قيد التحديث. نلغي/نتجاهل نتائج الطلبات السابقة عند تغيير البحث، فلا تظهر نتيجة بحث قديم فوق الأحدث.

بحث الاقتراحات: debounce مبدئي 250–350ms بعد حروف كافية، مع request cancellation وحدّ نتائج؛ الرقم مقترح للضبط. إن تعقدت combobox، نبدأ ببحث عند submit بدل تجربة اقتراحات ناقصة الوصول. لا نستدعي API مع كل scroll أو render، ولا نكرر POST شراء بعد timeout تلقائيًا. [S03–S04، S19–S20]

## 11 — الحركة البسيطة

| التفاعل | الاقتراح | السبب |
| --- | --- | --- |
| hover زر/لون | 120–160ms | إحساس باستجابة سريعة |
| hover كارت | 160–180ms، translateY بحد أقصى 2px | إبراز بسيط دون تغيير حجم الشبكة |
| ظهور popover | 160–200ms، opacity + انتقال 4–8px | توضيح مصدر الطبقة |
| drawer/dialog | 200–240ms | دخول مفهوم مع تركيز صحيح |
| إضافة للسلة | تحديث badge ورسالة، بلا طيران منتج عبر الصفحة | تأكيد العملية دون تشتيت |
| loading | indicator محدود + aria-busy | لا وميض أو shimmer مستمر عبر الصفحة |

نستخدم CSS transition وkeyframes صغيرة. لا GSAP أو Framer Motion في البداية. لا parallax، ولا دوران 3D، ولا scroll hijacking، ولا autoplay فيديو. hero ثابت أو تنقل يدوي؛ أي carousel لاحق يحتاج تحكم كيبورد وإيقاف مناسب. hover لا يخفي زرًا أساسيًا على اللمس. `prefers-reduced-motion: reduce` يوقف الحركة غير الضرورية ويحافظ على ظهور الحالة النهائية. لا `transition: all`، ولا تحريك width/height للهيكل كله، ولا `will-change` على كل كارت. [S21]

## 12 — English أولًا، والعربية لاحقًا، والوصول

قرار المستخدم المؤكد: واجهة English فقط في المرحلة الأولى، بـlang="en" وdir="ltr". كل المتجر والحساب وصفحات البائع والإدارة ورسائل النجاح والخطأ والتحقق وتدفق الطلبات بالإنجليزية. التنسيق الافتراضي المقترح en-EG وعملة EGP حسب السوق. لا زر تغيير لغة ولا اكتشاف تلقائي للعربية قبل تنفيذها.

نجهز إضافة العربية بأقل بنية لازمة: نصوص UI الثابتة في كائن إنجليزي بسيط مقسم حسب الشاشة/المهمة، ومساعد تنسيق واحد يستخدم Intl؛ لا محرك ترجمة عام أو ملفات عربية وهمية. البيانات والوصف الآتيان من API ليسا نفس نصوص الواجهة، ونضيف ترجمتهم بعقد محتوى واضح في المرحلة اللاحقة. نستخدم من الآن خصائص margin-inline/padding-inline وtext-start لأنها تعمل مع LTR وتجعل التعديل اللاحق أسهل. [S22]

بعد اكتمال النسخة الإنجليزية ومراجعة آخر خطوة، نفتح L01: إضافة النصوص والمحتوى العربي، وإعداد lang/dir المناسب، والخط العربي، وحالات الجمع والتنسيقات، ثم اختبار كل رحلة وواجهة تشغيل في RTL. أرقام SKU والبريد والهاتف وروابط وأسماء الموديلات داخل bdi أو منطقة LTR مناسبة عند الحاجة. أسهم التنقل تتبع الاتجاه؛ أيقونات search/cart/check/play والشعارات لا تنعكس تلقائيًا. إضافة العربية ليست تبديل text-align فقط، ولا يُعد الإصدار الإنجليزي ناقصًا لغياب ميزة مؤجلة بقرار المستخدم.

التنقل بالكيبورد كامل، focus واضح لا تخفيه الأشرطة الثابتة، skip link، labels، رسائل حقول مرتبطة، alt للصور المفيدة وalt فارغ للزخرفية. اللون لا يحمل معنى وحده. نختبر تكبير النص 200% وإعادة التدفق عند عرض 320 CSS px؛ أجزاء مثل جداول المقارنة لها منطقة تمرير معنونة عند الحاجة. نحترم reduced motion والوضع عالي التباين قدر الإمكان. [S12–S14، S17]

على الهاتف: controls مناسبة للمس، لا وظائف تعتمد على hover، لا إضافة غير مقصودة أثناء السحب، لوحة المفاتيح لا تغطي الحقل والإجراء، sticky buy لا يغطي آخر محتوى، safe-area-inset-bottom عند الأشرطة السفلية، وعدم إقفال zoom. landscape واستخدام ماوس على تابلت أو لمس على لابتوب حالات طبيعية؛ لا نعتمد user-agent لاختيار التصميم.

## 13 — Architecture بسيطة قابلة للتعديل

التوصية: React + JavaScript/JSX + Vite + Tailwind. Router واحد للصفحات عند بدء التنفيذ، وأيقونات من عائلة واحدة باختيار imports محددة. نثبت نسخًا مستقرة متوافقة بعد فحص المشروع ونتيجة install/build، دون افتراض أن أحدث رقم موثق هو إصدار المشروع. Tailwind v4 يستخدم تكامل Vite وCSS theme؛ لا نخلط إعدادات v3 القديمة عشوائيًا. [S16، S23–S26]

| --- | --- |
| src/app | الدخول، routes، providers الضرورية |
| src/pages | تجميع كل شاشة؛ customer وseller وadmin عند الحاجة |
| src/components/ui | عناصر بسيطة مشتركة فعلًا: Button، Field، Dialog |
| src/components/layout | Header، Footer، StoreLayout، PortalLayout |
| src/features/catalog | ProductCard، Filters، Gallery، Compatibility |
| src/features/cart | CartContext وعمليات السلة |
| src/features/auth | حالة الدخول وتدفقه |
| src/lib | api.js وformat.js فقط عند الحاجة |
| src/styles | index.css وtokens.css وmotion.css إذا كبر الملف |
| src/mocks | fixtures واقعية في التطوير فقط |

هذا اقتراح مسارات، لا أمر بإنشاء مجلدات فارغة أو كل المكونات مرة واحدة. لا layer كاملة لكل عنصر؛ لا Redux افتراضيًا؛ لا generic repository في الفرونت؛ لا تخزين بيانات المنتجات كاملة في أكثر من context؛ لا component عملاق يبني كل الصفحات من config معقد.

state قريب من مكان استخدامه: useState للـdrawer والاختيارات، URL للفلاتر، CartContext صغير للسلة، وAuthContext إن احتجناه على أكثر من شاشة. نتجنب نسخ filteredProducts وtotal وselectedProduct إلى state لو يمكن اشتقاقها من البيانات الموجودة. server state يظل مرتبطًا بطلباته؛ caching library تُضاف فقط عند حاجة متكررة مثبتة. [S19–S20]

قواعد قراءة الكود: اسم يعبر عن المعنى؛ وظيفة واحدة واضحة؛ تفكيك الملف عندما يجمع مسؤوليات مختلفة أو يصعب استيعابه؛ لا ضغط أسطر لإظهار عدد أقل. مكون 150 سطرًا واضحًا أفضل من 50 سطرًا مختصرًا وغامضًا؛ هذه مقارنة توضيحية وليست حدًا إلزاميًا. التعليق يشرح سببًا غير بديهي؛ لا يعيد شرح السطر.

ألوان ومسافات أساسية في tokens واحدة. Tailwind يعرض layout وحالاته مباشرة. variants صغيرة كخريطة classes كاملة، لا أسماء مثل `bg-${color}-600` لأن Tailwind لا يكتشف الأجزاء الديناميكية بهذه الطريقة. قيم ديناميكية محدودة من بيانات موثوقة تستخدم CSS custom properties بعد التحقق، لا arbitrary classes آتية من API. [S27]

مثال conceptual لحركة واحدة، وليس بدءًا للتطبيق:

```css
.product-card { transition: transform 180ms ease; }
@media (hover: hover) and (prefers-reduced-motion: no-preference) {
  .product-card:hover { transform: translateY(-2px); }
}
@media (prefers-reduced-motion: reduce) {
  .product-card { transition: none; }
}
```

## 14 — الأداء والـSEO والربط الآمن

صور منتج contain، وأبعاد width/height وaspect-ratio معروفة لحجز مكانها. صور متعددة الدقات وsizes مناسبة، AVIF/WebP مع fallback إن لزم، lazy loading لما تحت أول شاشة؛ صورة LCP لا تُحمّل lazy. hero صورة متجاوبة وليست فيديو خلفية. تجزئة routes الثقيلة كالإدارة بدل تحميلها أول زيارة للمتجر. لا نضيف memo/useMemo لكل عنصر قبل وجود مشكلة فعلية.

أهداف تشغيلية: LCP ≤2.5s، INP ≤200ms، CLS ≤0.1 عند p75 من زيارات حقيقية، مع فصل mobile/desktop. هذه أهداف من web.dev، ولم تُقَس على مشروع لم يُبنَ. Lighthouse في المختبر إشارة تشخيص ولا يثبت نتائج المستخدمين. [S28]

روابط منتجات قابلة للفتح المباشر، عنوان وmetadata مناسبة لكل منتج، sitemap وcanonical مدروسان، structured data من بيانات المنتج الفعلية، وعدم فهرسة cart/account/admin. اختيار SPA/Vite بسيط للتطوير لا يحسم SEO الإنتاج: قبل الإطلاق نتحقق من ظهور المحتوى للمحركات ومشاركة الروابط، ونقرر prerender للصفحات العامة إن لزم دون تغيير التقنية المتفق عليها سرًا. structured data لا تضمن ظهور rich results. [S29]

API wrapper واحد يعالج الأخطاء وcredentials وAbortSignal؛ لا axios أو أدوات إضافية إذا fetch يفي بالغرض. أسرار الدفع والخدمات لا توضع في React أو متغيرات VITE العامة. عقود الجلسات والـCSRF تتبع ملف الأمان والباك اند. لا نعرض نجاح الدفع بناء على query string، ولا ندخل HTML بائع غير معقم بـdangerouslySetInnerHTML. مواصفات الحماية التفصيلية في `04_SECURITY.md`، ويجب تطبيقها أثناء الواجهة، لا تأجيلها لنهاية المشروع.

## 15 — خطة التنفيذ اللاحقة ومعايير المراجعة

لم يبدأ التنفيذ. عند طلبه، أول شريحة: tokens وheader وكارت منتج وقائمة صغيرة ببيانات تطوير معلنة، على 390 و1440، ثم تجربة عناوين إنجليزية طويلة وحالات loading/empty/error. تكتمل كل مراحل الإصدار الإنجليزي أولًا، ثم نضيف العربية في L01 ونكرر فحص الرحلات والـRTL دون إعادة بناء المكونات. نثبت المكون قبل نشره في كل الصفحات. نكمل PLP ثم PDP ثم cart/checkout ثم account ثم seller/admin حسب طلب المستخدم وتوفر العقود. لا نبني homepage نهائية كاملة قبل التحقق من الكارت والبحث والشراء.

| بوابة المراجعة | دليل القبول المطلوب عند التنفيذ |
| --- | --- |
| الألوان | فحص contrast للأزواج والحالات المستخدمة، لا اللون منفردًا |
| المقاسات | لقطات 360/390/768/1024/1280/1440 و320 reflow، مع عدم تمرير الصفحة أفقيًا |
| المحتوى | عنوان إنجليزي طويل، موديل/SKU، سعر كبير، بلا تقييم، صورة مفقودة، منتج غير متاح؛ العربية في L01 لاحقًا |
| الكارت | وضوح price/variant/spec وCTA، وعدم أزرار داخل رابط |
| البحث | URL/back، إلغاء نتائج قديمة، empty/error، navigation بالكيبورد إن وجدت اقتراحات |
| السلة والدفع | بائعان، تغير سعر، نقص مخزون، timeout، pending/unknown، وانتهاء جلسة دون فقد سياق |
| الوصول | keyboard، focus، labels، تكبير، reduced motion، وسلوك dialog فعلي |
| جودة الكود | سهولة تعديل لون/كارت/endpoint من موقع معروف؛ لا تكرار بيانات أو abstractions غير لازمة |
| الأداء | build وتحليل صور وحجم الحزم، ثم قياس مخبري مع إعداداته؛ الميداني بعد إطلاق مناسب |
| اكتمال الادعاء | الدراسة ليست كودًا؛ mock ليس تكاملًا؛ build ليس اختبار دفع حيًا |

مفتوح قبل تثبيت الهوية النهائية: اسم المنصة، اختيار palette، الخط بعد تجربة نص حقيقي، كثافة الكروت، الصور المرخصة، ونطاق أول شريحة تنفيذ. القيم الحالية baseline مقترح يمكن تعديله؛ لا حاجة لإعادة البحث كله عند تعديل لون.

## 17 — حالة التسليم

ترتيب اللغات مؤكد: English/LTR أولًا حتى اكتمال المراجعة، ثم العربية/RTL. تم: تفكيك المراجع، تحديد اتجاه مقترح، تصميم baseline للمقاسات والألوان والمكونات والحركة، هيكل frontend بسيط، وربطها بمعايير قبول. لم يتم: بناء React، اختبار browser للواجهة، اختبار مستخدمين، قياس أداء، اعتماد هوية نهائية. يُستخدم `02_FRONTEND_PENDING.md` كملخص handoff باللغة الإنجليزية؛ اسمه محفوظ للتوافق مع حزمة الملفات السابقة، ومحتواه لم يعد placeholder فارغًا.
